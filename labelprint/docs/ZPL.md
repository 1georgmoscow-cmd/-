# Формат ZPL: то, что обязан соблюдать кодировщик

Справка по деталям, которые ломают печать молча, без сообщений об ошибке.
Всё сверено с *ZPL II Programming Guide* (Zebra) и спецификацией Netpbm.

## Полярность и раскладка бит

Бит `1` печатает **чёрную** точку, бит `0` — белую. Старший бит байта — самая
**левая** точка. Каждая строка растра дополняется до целого числа байт.

Первоисточник — описание `~DG` в мануале: «если первые четыре точки изображения
белые, а следующие четыре чёрные, двоичный код 00001111, шестнадцатеричное
представление 0F».

PBM P4 (то, что отдаёт `gs -sDEVICE=pbmraw`) устроен ровно так же: `1` — чёрный,
старший бит слева, строки выровнены по байту. **Инверсия между PBM и ZPL не нужна.**
Единственная обязательная операция — обнулить биты-заполнители правее ширины
изображения, иначе по правому краю каждой этикетки пойдёт чёрная полоса.

## Команда ^GF

```
^GFa,b,c,d,данные
```

| Параметр | Значение |
|---|---|
| `a` | `A` — ASCII-hex, `B` — двоичные данные, `C` — сжатые двоичные (алгоритм Zebra не опубликован, не использовать) |
| `b` | число байт несжатого растра |
| `c` | то же значение; отличается от `b` только для `^GFC` |
| `d` | число байт в строке = `ceil(ширина / 8)` |

Используется только `^GFA`. Данные остаются печатным ASCII, поэтому поток
безопасно хранить в базе и передавать по любому каналу. `^GFB` содержит байты
`0x00`, `0x0A`, `0x0D` и будет испорчен первым же преобразованием переводов строк.

`b = c = d * высота` — **всегда**, в том числе для сжатых ACS и `:Z64:`. В мануале
это сказано прямо: «For ASCII download, the parameter should match parameter c»,
а приложение про ZB64 добавляет: «это поле должно содержать размер объекта без
обёртки и без сжатия — число байт, которые в итоге попадают в память принтера,
а не число переданных байт».

Все три параметра `b`, `c` и `d` имеют умолчание «command is ignored if a value is
not specified»: пропущенный параметр не заменяется нулём, а тихо отменяет всю
команду `^GF`. Ошибки не будет — будет пустая этикетка.

### Расхождение спецификации и прошивок

Мануал документирует для `b`, `c` и `d` диапазон **1..99999** и добавляет:
«Out-of-range values are set to the nearest limit». Между тем:

| Этикетка | c = байт в строке × высота | В пределах? |
|---|---|---|
| 58×40 мм при 203 dpi | 18 560 | да |
| 58×40 мм при 300 dpi | 40 592 | да |
| 100×150 мм при 203 dpi | 120 000 | **нет** |
| 4×6 дюйма при 203 dpi | 124 236 | **нет** |
| 4×6 дюйма при 300 dpi | 270 000 | **нет** |

Прочитанное буквально, это означало бы обрезку этикетки 4×6 примерно на 80 процентов.
На практике прошивки принимают большие значения — их же выдаёт и сам ZebraDesigner, —
поэтому labelprint выводит `b = c` как есть. Но если этикетка печатается обрезанной
сверху на конкретной модели, причина может быть именно здесь. `bin/doctor.php`
предупреждает о профилях, выходящих за документированный предел.

### Про `^FS`

Данные `^GF` завершаются **по счётчику байт**, а не разделителем: «The number of
two-digit number pairs must match the above count. Any numbers sent after count is
satisfied are ignored». `^FS` ставится после команды как обычный разделитель полей,
а не как терминатор данных. Практическое следствие: если `b` посчитан неверно и
`^FS` уходит раньше, чем набрано `b` байт, его три байта `5E 46 53` будут
восприняты как данные изображения — строки съедут, а следующие команды будут съедены.

Символы `^` и `~` внутри данных обрывают загрузку изображения («~DN or any caret or
tilde character prematurely aborts the download»). Внутри hex-данных допустимы CR и
LF (принтер их игнорирует), но не пробелы и не табуляции.

## Сжатие ACS

Побайтовый RLE поверх **шестнадцатеричного** представления. Счётчик относится
к следующему одному hex-символу, то есть к четырём точкам по горизонтали.

Формально приложение мануала называется «Alternative Data Compression Scheme for
~DG and ~DB Commands» и перечисляет только `~DG` и `~DB`. Для самой команды `^GF`
документирована лишь запятая. Тем не менее ACS работает и с `^GFA`: приложение про
ZB64 прямо говорит, что при загрузке графики двоеточие в текущей шестнадцатеричной
кодировке означает «повторить предыдущую строку точек». На этом и стоит вся
практика — включая вывод ZebraDesigner.

| Символы | Значение |
|---|---|
| `G`…`Y` | 1…19 повторов |
| `g`…`z` | 20, 40, 60, … 400 повторов |

Счётчики складываются, порядок неважен: `vMB` и `MvB` одинаково означают 327 символов `B`
(320 + 7). Максимум в одной группе — `zY`, то есть 419. Более длинные прогоны выводятся
несколькими группами.

Три спецсимвола, каждый завершает строку растра:

| Символ | Действие |
|---|---|
| `,` | добить строку нулями (белым) до конца |
| `!` | добить строку символами `F` (чёрным) до конца |
| `:` | повторить предыдущую строку целиком |

### Два правила, которые легко нарушить

**Первым символом данных `:` быть не может.** Ведущее двоеточие — это признак
конверта `:B64:`/`:Z64:`, и принтер попытается разобрать всю графику как испорченный
ZB64. Строка 0 всегда выводится литералом (или `,` / `!`).

**Перед `,` и `!` должно остаться чётное число литеральных полубайт.** Мануал
(*Advanced Techniques*, «Reducing Download Time of Graphic Images»): «если
hex-строка заканчивается чётным числом нулей, все нули заменяются одной запятой;
если нечётным — нужен один ноль и запятая». Строка `1000` кодируется как `10,`,
а не `1,`.

Кодировать нужно строго построчно: `,`, `!` и `:` действуют в пределах одной строки,
и прогон, пересекающий границу строк, даёт диагональный сдвиг. Изображение при этом
внешне похоже на правильное, а штрихкод не читается.

## Конверт :Z64:

```
:Z64:<base64 от zlib-потока>:<CRC, 4 hex-символа>
```

* `:B64:` — только base64, без сжатия (+33 % к размеру).
* `:Z64:` — сначала deflate, потом base64.
* Сжатие — **zlib** (RFC 1950, заголовок `78 9C`), то, что даёт `gzcompress()` в PHP.
  Голый deflate без заголовка — единственный вариант, для которого нет подтверждений,
  что принтеры его принимают.
* CRC считается **по тексту base64**, а не по двоичным данным. Используется
  CRC-16/XMODEM: полином `0x1021`, начальное значение `0x0000`, без отражения бит
  и без финального XOR. Контрольный вектор: `CRC("123456789") = 0x31C3`.

`:Z64:` допустим только после `^GFA` — не после `^GFB` и не после `^GFC`.

На практике прошивки не проверяют CRC строго: три распространённые библиотеки
считают его тремя несовместимыми способами, и все печатают. Но это значит и обратное —
на расхождение CRC нельзя опереться как на диагностику.

Поддержка: `:Z64:` уверенно работает на Zebra Link-OS. Клоны с ZPL-эмуляцией
(TSC ZGL, Godex GZPL, Xprinter) нередко понимают только обычный hex и иногда ACS.
Для смешанного парка безопаснее ACS.

## Команды, состояние которых «липнет»

Все они переживают перезагрузку принтера, если были сохранены через `^JUS`,
и портят каждую следующую этикетку **без каких-либо сообщений**. Задание,
собираемое labelprint, сбрасывает их явно:

| Команда | Что будет, если оставить чужое значение |
|---|---|
| `^MUd` | координаты пересчитываются в дюймы или сантиметры |
| `^JMA` | при `^JMB` разрешение вдвое ниже, а все координаты вдвое больше |
| `^LH0,0` | сдвинуто начало координат |
| `^LT0` | формат сдвинут по вертикали |
| `^LS0` | формат сдвинут по горизонтали |
| `^PON` | при `^POI` этикетка перевёрнута на 180° |
| `^PMN` | при `^PMY` этикетка зеркальная |
| `^LRN` | при `^LRY` печатается негатив |
| `^MCY` | при `^MCN` предыдущая этикетка проступает на следующей |
| `^PW` | по умолчанию берётся «последнее сохранённое значение» — узкий `^PW` обрезает штрихкод |

## Геометрия

* `^PW<точки>` — ширина печати. Всё правее обрезается.
* `^LL<точки>` — длина этикетки. Обязательна на непрерывной ленте.
* `^FO0,0` — левый **верхний** угол поля. У `^FT` начало координат для изображения —
  левый **нижний** угол, поэтому `^FT0,0^GFA…` выталкивает растр за верхний край.
* Пересчёт: 203 dpi = 8 точек/мм, 300 dpi = 11,8 точек/мм.
  100×150 мм при 203 dpi — 799×1199 точек, при 300 dpi — 1181×1772.
* Ширина головки: 4 дюйма — 832 точки при 203 dpi и 1248 при 300 dpi; 58 мм — 464 точки.

Растр, отрендеренный под 300 dpi, на головке 203 dpi окажется в полтора раза больше
и будет обрезан; растр под 203 dpi на головке 300 dpi напечатается в углу в две трети
размера. Ни то, ни другое не вызывает ошибки — рендерить нужно ровно под разрешение головки.

## Чего не делать

* **Не дизерить растр.** Этикетка — это штриховая графика и штрихкоды. Диффузия ошибки
  разбрасывает одиночные точки по краям штрихов и в зонах молчания, после чего сканер
  штрихкод не берёт. Только жёсткий порог.
* **Не хранить `~DG` в `E:`** (флеш): у каждой этикетки уникальный штрихкод, переиспользования
  нет, а ресурс перезаписи конечен. Для одноразовой графики используется `^GF` внутри задания.
* **Не рассчитывать на `^XG` для масштабирования**: увеличение только целое, от 1 до 10,
  уменьшения нет вовсе.
* **Не выводить одновременно `~SD` и `^MD`**: `~SD` абсолютный, `^MD` относительный,
  и мануал говорит, что значения складываются — получится двойная температура.
* **Не класть `~JC` (калибровку) и `^JUS` (сохранение настроек) в задание этикетки**:
  первая тратит ленту на каждой этикетке, вторая пишет в энергонезависимую память.
