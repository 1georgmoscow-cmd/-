# labelprint — воркер рендеринга PDF в ZPL

Сервис для Ubuntu: следит за каталогом с PDF-этикетками, рендерит каждую страницу
в ZPL и складывает готовые к отправке байты в MySQL. Печатью занимается отдельный
потребитель — он просто читает строку из таблицы и пишет её в принтер.

Composer не нужен: достаточно PHP 8.1+, Ghostscript и MySQL.

## Зачем это

Термопринтер не понимает PDF. Обычно PDF отдают драйверу Windows, тот растеризует
его и гонит в принтер огромный битмап — полторы-четыре секунды на этикетку.

Здесь тяжёлая работа делается заранее и один раз: как только PDF появился в каталоге,
воркер превращает его в ZPL. В момент печати остаётся прочитать готовые байты из базы
и записать их в сокет — это десятки миллисекунд.

```
/upload/pdf/*.pdf
      │
      │  bin/scan.php --watch     (наблюдение за каталогом)
      ▼
  pdf_files ──▶ render_jobs (очередь, MySQL)
                     │
                     │  bin/worker.php  x N процессов
                     │
                     ├── 1. захват задания   SELECT ... FOR UPDATE SKIP LOCKED
                     ├── 2. Ghostscript      PDF -> 8 бит серого, одним вызовом на все страницы
                     ├── 3. порог            серое -> 1 бит, без полутона (иначе штрихкод не читается)
                     ├── 4. поворот          если страница лежит боком
                     ├── 5. ^GFA + сжатие    ACS или :Z64:
                     ├── 6. самопроверка     распаковать обратно и сверить с растром
                     └── 7. запись           zpl_labels
                                  │
                                  ▼
                        любой потребитель: PHP/JS/что угодно
                        читает zpl и пишет в printer_ip:9100
```

## Что даёт скорость

| Решение | Эффект |
|---|---|
| Рендеринг заранее, до нажатия «Печать» | секунды уходят из момента печати в фон |
| Ключ кэша — SHA-256 содержимого PDF | тот же файл под другим именем не рендерится повторно |
| Все страницы одним вызовом растеризатора | запуск процесса — самая дорогая часть, платим один раз за файл |
| Движок MuPDF вместо Ghostscript | 15,5 мс на страницу вместо 47 |
| Бинаризация строками, а не пикселями | 10 мс вместо 50 на этикетку |
| Сжатие ACS или Z64 | 240 КБ сырого hex превращаются в 17 КБ или 11 КБ |
| Воркеров столько же, сколько ядер | растеризация упирается в процессор и хорошо параллелится |

Замерено на настоящем конвейере: Ubuntu 24.04, 4 ядра, Ghostscript 10.02 / MuPDF 1.23,
MariaDB 10.11, этикетки 100×150 мм при 203 dpi (растр 800×1199).

| Этап | Ghostscript | MuPDF |
|---|---|---|
| Растеризация страницы | 47 мс | 15,5 мс |
| Бинаризация по порогу | 10 мс | 10 мс |
| Кодирование ZPL (ACS) | 2,7 мс | 2,7 мс |
| Самопроверка | 2,7 мс | 2,7 мс |
| Запись в MySQL | 2–5 мс | 2–5 мс |
| **Пропускная способность, 4 воркера** | **2380 этикеток/мин** | **3160 этикеток/мин** |

Разница между движками почти целиком в запуске процесса: Ghostscript тратит на
инициализацию интерпретатора около 43 мс, MuPDF стартует за миллисекунды.
Ghostscript при этом терпимее к повреждённым PDF, поэтому он оставлен движком
по умолчанию, а MuPDF включается параметром `engine` в профиле.

Размер ZPL для той же этикетки:

| Кодирование | Размер | Совместимость |
|---|---|---|
| `hex` | ~240 КБ | любой ZPL-принтер, для отладки |
| `acs` | ~31 КБ | любой ZPL-принтер с середины 1990-х |
| `z64` | ~14 КБ | Zebra Link-OS и современные прошивки |

По умолчанию стоит `acs` — он работает и на китайских клонах с ZPL-эмуляцией.
Если парк целиком из настоящих Zebra, ставьте `z64`: он и вдвое компактнее, и быстрее
кодируется. Можно завести два профиля на одну этикетку и хранить обе версии.

## Требования

```bash
sudo apt install php-cli php-mysql php-mbstring \
                 ghostscript poppler-utils mupdf-tools \
                 zbar-tools dmtx-utils
```

* PHP 8.1+ с расширениями `pdo_mysql`, `zlib`, `mbstring`, `pcntl`
* Ghostscript 9.50+ (в Ubuntu 22.04/24.04 — из коробки)
* MySQL 8.0+ или MariaDB 10.6+ (на более старых работает запасной способ захвата задач)
* `mupdf-tools` не обязателен, но даёт втрое более быструю растеризацию
* `poppler-utils` не обязателен, но с ним точнее определяется ориентация страницы
* `zbar-tools` нужен для распознавания QR и штрихкодов на этикетке
* `dmtx-utils` нужен, только если на этикетках есть DataMatrix («Честный знак»)

## Установка

```bash
sudo bash deploy/install.sh              # пакеты, копирование в /opt/labelprint, юниты systemd
mysql -u root -p < db/schema.mysql.sql   # база и таблицы
cd /opt/labelprint
cp config/config.example.php config/config.php
cp config/printers.example.php config/printers.php
$EDITOR config/config.php                # доступ к базе и путь к каталогу с PDF
php bin/doctor.php                       # проверка окружения
```

`bin/doctor.php` проверяет ровно то, из-за чего сервис молча не работает после
развёртывания: нет Ghostscript, воркеру не хватает прав на `/upload/pdf`,
мал `max_allowed_packet`, не применена схема, MySQL старее 8.0.

## Запуск

```bash
sudo systemctl enable --now labelprint-scanner          # наблюдение за каталогом, один экземпляр
sudo systemctl enable --now labelprint-worker@{1..4}    # воркеры, по числу ядер
journalctl -u 'labelprint-*' -f
```

Пароль к базе лучше держать вне репозитория — раскомментируйте `EnvironmentFile`
в юните и положите в `/etc/labelprint/env`:

```
LABELPRINT_DB_PASSWORD=...
```

Переменные окружения перекрывают конфиг по правилу `db.password` → `LABELPRINT_DB_PASSWORD`.

## Настройка профилей

Профиль описывает этикетку и принтер. Его параметры входят в ключ кэша: поменяли
разрешение — воркер автоматически перерендерит всё под новый профиль.

```php
'zebra_203_100x150' => [
    'dpi'            => 203,
    'width_mm'       => 100,
    'height_mm'      => 150,
    'fit'            => 'fit',      // вписать страницу в этикетку; 'native' — взять размер из PDF
    'auto_rotate'    => true,       // довернуть, если страница лежит боком
    'threshold'      => 128,        // порог бинаризации, 1..254
    'compression'    => 'acs',      // acs | z64 | hex
    'engine'         => null,       // ghostscript | mupdf | auto | null (из config.php)
    'printhead_dots' => 832,        // ширина головки; шире — ошибка вместо обрезанного штрихкода
    'darkness'       => null,       // ^MD; null — не трогать настройку принтера
    'media_tracking' => 'gap',      // gap | mark | continuous | null
],
```

Какие профили применять к новым файлам, задаётся в `config.php`:

```php
'scanner' => ['profiles' => ['zebra_203_100x150', 'zebra_300_100x150']],
```

## Распознавание кодов и сверка со сканером

Воркер распознаёт коды на этикетке и кладёт их в таблицу `label_codes`. Это закрывает
складской процесс целиком:

```
сканируется ШК товара ──▶ печать ZPL-этикетки ──▶ наклеили ──▶ сканируем наклеенную
                                                                      │
                                          сверка с label_codes ◀──────┘
```

Ключевая деталь: распознаётся **не исходный PDF, а тот самый однобитный растр**,
который через мгновение уедет на принтер. Смысл именно в этом. Если код не читается
отсюда, его не прочтёт и сканер на складе — и брак виден на этапе рендеринга,
а не после того, как этикетку наклеили на коробку. Этикетка без единого кода
отмечается в логе предупреждением.

| Символика | Чем читается | Цена на этикетку 800×1199 |
|---|---|---|
| QR-Code, CODE-128, CODE-39/93, EAN/UPC, ITF, Codabar, DataBar | `zbarimg` | ~40 мс |
| DataMatrix, то есть «Честный знак» | `dmtxread` | ~210 мс |

DataMatrix по умолчанию выключен: он впятеро дороже, а на этикетках маркетплейсов
его обычно нет. Включается в `config.php` — `barcode.dmtx => true`.

### Этикетки OZON

Проверено на настоящей этикетке. Что важно знать:

| Свойство | Значение |
|---|---|
| Размер страницы | 164,25 × 113,25 pt = **58 × 40 мм, альбомная** |
| Растр при 203 dpi | 464 × 320 точек |
| Штрихкод | нарисован **векторно**, не картинкой |
| Машиночитаемый код | **один QR**, около 205 × 205 точек |
| DataMatrix («Честный знак») | отсутствует — `barcode.dmtx` держите выключенным |
| Рендеринг с распознаванием | ~96 мс, ZPL около 10,7 КБ |

Готовый профиль — `ozon_203_58x40` (и `ozon_300_58x40` для 300 dpi).

Две особенности, о которые легко споткнуться:

**Содержимое свёрстано повёрнутым.** Номер отправления и логотип читаются вдоль
длинной стороны. Так и печатает OZON, ничего доворачивать не надо: ориентация
страницы (альбомная) совпадает с ориентацией профиля, поэтому `auto_rotate`
не срабатывает. Если завести профиль 40 × 58, авто-поворот развернёт этикетку — это
будет неверно.

**В QR лежит не тот номер, что напечатан текстом.** На этикетке крупно написано
что-то вроде `0494 0518 -0963-1`, а в QR — отдельный числовой идентификатор
(15 цифр). Сканер вернёт именно содержимое QR, поэтому сверять в вашей системе
надо с ним, а не с распознанным глазами номером отправления.

Распознавание проверено на 203, 300 и 600 dpi при порогах бинаризации от 96 до 190 —
QR читается во всех сочетаниях. На 203 dpi распознавание занимает около 13 мс:
этикетка мелкая, и это заметно быстрее, чем 40 мс на 100 × 150 мм.

### Сверка

```bash
php bin/verify.php --file=wb-12345.pdf "WB-1234567890-BOX3"   # то ли наклеили?
php bin/verify.php "4607428561111"                             # чья это этикетка?
php bin/verify.php --file=wb-12345.pdf --json "…"              # для вызова из программы
```

Код возврата: `0` — совпало, `1` — нет. Из своего кода то же самое одним запросом:

```sql
SELECT 1 FROM label_codes
 WHERE zpl_label_id = ?
   AND (value_sha1 = SHA1(?) OR normalized_sha1 = SHA1(?));
```

Значения хранятся в двух видах — как есть и без управляющих байтов. Это не
перестраховка: код «Честного знака» содержит разделители `GS` (0x1D), и ручные
сканеры обходятся с ними по-разному — одни отдают как есть, другие выбрасывают,
третьи заменяют. Сравнение по одному варианту давало бы ложные несовпадения.
По той же причине колонка `value` имеет тип `VARBINARY`, а не текстовый.

Обратный поиск — по считанному коду найти этикетку — идёт по индексу
`idx_code_value` / `idx_code_normalized`.

## Встраивание в свой код

Установка по шагам — [docs/INSTALL.md](docs/INSTALL.md), использование —
[docs/USAGE.md](docs/USAGE.md), примеры — [examples/](examples/). Кратко:

```php
require '/opt/labelprint/src/bootstrap.php';

$api = LabelPrint\Api::boot();

// PDF скачан из API OZON по номеру отправления
$label = $api->savePosting($postingId, $pdfBytes);

$zpl     = $label->zpl;       // текст этикетки на языке ZPL
$barcode = $label->barcode;   // распознанный QR для сверки, '751466115153000'

$api->send($zpl, '192.168.1.50');          // печать, ~0,5 мс
$api->verify($label->id, $scanned);        // сверка после наклейки
```

Повторно по номеру — `$api->byPosting($postingId)`, около 1 мс из кэша.

## Как забрать ZPL и напечатать

Готовые этикетки лежат в `zpl_labels`, по строке на страницу:

```sql
SELECT page_no, zpl, width_dots, height_dots, dpi
  FROM zpl_labels
 WHERE pdf_sha256 = ? AND profile_code = ?
 ORDER BY page_no;
```

Отправка на сетевой принтер — это буквально запись в сокет:

```php
$zpl = ''; // склеенные страницы из выборки выше
$socket = stream_socket_client('tcp://192.168.1.50:9100', $errno, $error, 3);
stream_set_timeout($socket, 5);
fwrite($socket, $zpl);
fclose($socket);
```

Найти этикетку можно по номеру отправления или по имени файла. Ключевое условие —
поиск по `pdf_sha256`, а не соединение по `pdf_file_id`:

```sql
-- По номеру отправления
SELECT l.id, l.zpl, c.value AS barcode
  FROM zpl_labels l
  LEFT JOIN label_codes c ON c.zpl_label_id = l.id
 WHERE l.pdf_sha256 = (SELECT sha256 FROM pdf_files WHERE posting_id = ? ORDER BY id DESC LIMIT 1)
   AND l.profile_code = ?
 ORDER BY l.page_no;
```

Искать надо именно по `pdf_sha256`, а не соединением по `pdf_file_id`. Кэш
контент-адресуемый: два отправления с побайтово одинаковой этикеткой делят одну
строку в `zpl_labels`, и соединение по идентификатору файла нашло бы её только
для того, что отрендерился последним.

```sql
-- По имени файла
SELECT l.zpl FROM zpl_labels l
 WHERE l.pdf_sha256 = (SELECT sha256 FROM pdf_files WHERE path = ?)
   AND l.profile_code = ?
 ORDER BY l.page_no;
```

Обращение к `pdf_files.sha256` через подзапрос заодно гарантирует, что вернётся
только ТЕКУЩАЯ версия файла: если PDF перезаписали по тому же пути, этикетки
прошлой версии остаются в базе до `bin/status.php --prune`.

Накопившиеся записи прошлых версий убираются командой `php bin/status.php --prune`.

Колонка `zpl` — это `MEDIUMBLOB` с готовым потоком `^XA…^XZ`. Ничего добавлять
или экранировать не нужно, задание самодостаточно.

## Инструменты командной строки

```bash
php bin/doctor.php                                  # проверка окружения
php bin/status.php --failures                       # состояние очереди и последние ошибки
php bin/status.php --retry-failed                   # вернуть упавшие задания в очередь
php bin/status.php --retry-dead                     # вернуть и тупиковые тоже
php bin/status.php --prune                          # убрать этикетки старых версий файлов
php bin/scan.php                                    # разовый обход каталога
php bin/worker.php --once --with-scanner            # разобрать очередь и выйти (для cron)
php bin/render.php label.pdf --stdout > label.zpl   # отрендерить один файл, не трогая базу
php bin/render.php label.pdf --preview=out.pbm      # сохранить растр и посмотреть глазами
php bin/render.php label.pdf --codes                # показать распознанные коды
php bin/verify.php --file=label.pdf "СЧИТАННОЕ"     # сверить с показаниями сканера
php bin/render.php label.pdf --force                # перерендерить в обход кэша
php tests/run.php                                   # тесты (Ghostscript и MySQL не нужны)
```

`--preview` — самый быстрый способ проверить новый профиль: PBM открывается любым
просмотрщиком, и сразу видно, не перевёрнута ли этикетка и не съехали ли поля.

## Схема базы

| Таблица | Назначение |
|---|---|
| `pdf_files` | найденные PDF: путь, SHA-256, размер, mtime, число страниц |
| `render_jobs` | очередь: состояние, попытки, аренда, задержка повтора, текст ошибки |
| `zpl_labels` | готовый ZPL: по строке на страницу под профиль |
| `label_codes` | коды, распознанные на этикетке: значение, символика, качество, координаты |

В `pdf_files` есть колонка `posting_id` — номер отправления маркетплейса. Он
проставляется либо явно (`Api::savePosting()`), либо выводится из имени файла
по шаблону `scanner.posting_id_pattern`.

Ключ кэша в `zpl_labels` — `(pdf_sha256, profile_fingerprint, page_no)`. Он контент-адресуемый,
поэтому повторная загрузка того же файла под новым именем не вызывает повторного рендеринга,
а изменение параметров профиля само по себе создаёт новую запись.

Захват заданий атомарен. На MySQL 8 используется `SELECT … FOR UPDATE SKIP LOCKED`:
воркеры разбирают разные строки, а не выстраиваются в очередь на одну. На 5.7 работает
запасной вариант `UPDATE … ORDER BY … LIMIT 1` с уникальным `claim_token`, по которому
воркер потом безошибочно находит именно своё задание.

Соединение воркера работает в режиме `READ COMMITTED`. Это не косметика: `SKIP LOCKED`
пропускает заблокированные записи, но не пропускает gap-блокировки, а под стандартным
`REPEATABLE READ` запрос захвата берёт next-key блокировки на диапазон индекса и
блокирует вставку новых заданий — воркеры начинают тормозить сканер ровно тогда,
когда очередь наполняется.

Задание, на котором воркер **падает** (нехватка памяти, SIGKILL, сбой в библиотеке),
не доходит до обработчика ошибок. Раньше такое задание возвращалось в очередь по
истечении аренды и убивало следующий воркер — и так по кругу. Теперь после исчерпания
попыток оно переводится в состояние `dead`, больше не выдаётся и видно в `bin/status.php`.

## Если что-то пошло не так

| Симптом | Причина |
|---|---|
| Этикетка чёрная целиком | инверсия: проверьте `invert` в профиле; воркер пишет об этом в лог по доле чёрного |
| Правый край обрезан вместе со штрихкодом | растр шире `^PW` или головки: задайте `printhead_dots` и получите ошибку вместо брака |
| Этикетка печатается вдвое крупнее и не влезает | в принтере остался `^JMB` от прошлого задания — задание labelprint сбрасывает это само |
| Штрихкод не сканируется | включено полутоновое растрирование или неверный dpi: рендерите ровно под разрешение головки |
| Этикетка перевёрнута | ориентация страницы PDF: включите `auto_rotate` или задайте `rotate` явно |
| `MySQL server has gone away` | воркер переподключается сам; если повторяется — поднимите `wait_timeout` |
| ZPL не записывается в базу | мал `max_allowed_packet`, поставьте 64M |
| Файл подхватился недописанным | увеличьте `scanner.min_age_sec` или пишите во временное имя и делайте `rename()` |
| Задание висит в состоянии `running` | воркер умер; через `worker.lease_sec` задание вернётся в очередь само |
| Задание в состоянии `dead` | воркер падал на нём до исчерпания попыток (нехватка памяти, битый PDF). Разберитесь с файлом, затем `php bin/status.php --retry-dead` |
| Имя файла с русскими буквами не подхватывается | колонка `path` должна быть `VARBINARY`; проверьте, что схема применена из текущей версии |
| «на этикетке не найдено ни одного кода» | код слишком мелкий для 203 dpi, попал под обрезку или у DataMatrix нет «тихой зоны». Посмотрите растр: `php bin/render.php ФАЙЛ --preview=out.pbm --codes` |
| Сканер читает этикетку, а сверка не проходит | сканер иначе обходится с разделителем `GS`; сверка уже учитывает оба варианта, проверьте `bin/verify.php --json` |
| DataMatrix не распознаётся | включён ли `barcode.dmtx`, и есть ли вокруг символа белое поле — libdmtx без «тихой зоны» его не видит |
| Сменили движок, а ZPL старый | движок входит в отпечаток профиля, перерендер запустится сам при следующем сканировании |

## Тесты

```bash
php tests/run.php
```

80 тестов, ни Ghostscript, ни MySQL для них не нужны. Покрыто то, что ломается тихо:

* поворот растра сверяется с наивной эталонной реализацией на ширинах, кратных и не кратных 8;
* сжатие ACS проверяется полным круговым преобразованием, включая прогоны длиннее 419 символов
  и правило чётности полубайт перед `,` и `!`;
* CRC для `:Z64:` сверяется с контрольным вектором `CRC-16/XMODEM("123456789") = 0x31C3`;
* растеризатор тестируется с подставным `gs`, в том числе на 400 КБ в stdout вместе с 200 КБ
  в stderr — так проверяется, что чтение каналов не приводит к взаимоблокировке;
* быстрая бинаризация сверяется с попиксельной на всех порогах и ширинах;
* выбор поворота проверяется на альбомных страницах, на `/Rotate 90` и на явных настройках;
* самопроверка `^GFA` ловит намеренно испорченное поле.

Отдельно конвейер прогонялся вживую на Ubuntu 24.04 с настоящими Ghostscript, MuPDF и
MariaDB: 45 заданий четырьмя воркерами разбираются без единого повторного захвата
(у всех заданий ровно одна попытка), ZPL проходит через `MEDIUMBLOB` побайтово,
битые PDF уходят в `failed` после повторов с задержкой, аренда умершего воркера
возвращает задание в очередь, а обрыв соединения с базой лечится переподключением.

Подробности по формату ZPL и ссылки на первоисточники — в [docs/ZPL.md](docs/ZPL.md).
